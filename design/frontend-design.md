# CF Platform 前端 UI/UX 设计 v1.0

> 类型：Operate 型产品工作台
> 目标：让普通用户不理解 Agent、CFProgram、FlowPlan、Trace 或 Ledger，也能完成“创建流程 → 测试 → 发布 → 运行 → 查看结果”。
> 约束：界面克制简约；一个页面一个主任务；高级技术信息渐进式披露；不改变 CF/Flow 两级架构。
> 依赖：[`product-design.md`](./product-design.md)、[`CF-design.md`](./CF-design.md)

---

## 1. 设计结论

CF Platform 的前端不应该看起来像：

- Agent 管理后台；
- JSON 编辑器；
- n8n 式复杂自动化画布；
- IDE；
- 充满日志和调试信息的运维面板。

它应该像一个安静、可靠的“流程工作台”：

```text
我想完成什么？
  ↓
系统给出可编辑的流程草案
  ↓
我确认每一步和权限
  ↓
系统测试并告诉我能否运行
  ↓
我发布一个版本
  ↓
我运行它并看到清晰结果
```

### 1.1 首要体验原则

1. **先说目标，再看流程**：普通用户可以从自然语言目标开始，不必先理解 CF。
2. **先看业务语言，再看技术细节**：默认显示“读取邮件”“整理风险”“生成报告”，不显示 Step index、span 或 JSON。
3. **一个页面一个主要动作**：页面明确告诉用户下一步做什么。
4. **危险动作提前解释**：写文件、发邮件、执行命令、访问外部资源，在运行前明确提示。
5. **不让用户编辑编译产物**：用户编辑 CFDraft/FlowDraft；CFProgram/FlowPlan 只读查看。
6. **状态比日志重要**：先说明“现在发生什么、是否需要你处理”，再提供技术证据。
7. **默认安全，明确授权**：不自动扩大权限、不自动换 Agent、不自动重试未知副作用。
8. **保留熟悉交互**：标准按钮、表单、抽屉、确认框、状态标签，不用新奇手势替代标准行为。

## 2. 用户与任务模型

### 2.1 普通用户

主要任务：

- 创建一个能解决实际工作的 Flow；
- 修改流程步骤和顺序；
- 处理测试错误；
- 发布和重复运行；
- 查看产物和失败原因。

普通用户不需要理解：

- AgentExecutor 的协议；
- ACP、Process、SDK 的差异；
- CFProgram 的局部 PC；
- Trace parent/link；
- Run Ledger 的实现。

### 2.2 高级用户/维护者

主要任务：

- 编写和发布 CFDraft；
- 管理 CFVersion；
- 管理 Executor Profile；
- 审阅权限、effects 和运行证据；
- 排查失败和 needs-reconciliation。

高级用户可以打开“技术详情”，但技术详情不能取代普通业务视图。

## 3. 信息架构

一级导航保持五项，不增加“Agents”一级入口：

```text
Flows
CF Library
Runs
Resources
Governance
```

### 3.1 Flows

默认首页。回答：

> 我有哪些流程？最近哪些流程需要我处理？

内容：

- 最近使用的 Flow；
- 草稿；
- 等待发布；
- 最近失败；
- 等待审批；
- 运行中；
- “新建 Flow”主按钮。

### 3.2 CF Library

能力函数库。回答：

> 我可以复用哪些能力？

普通视图显示：

- CF 名称；
- 一句话说明；
- 输入/输出摘要；
- 是否已发布；
- 被多少个 Flow 使用。

维护者视图增加：

- Source；
- Compile；
- Test；
- Versions；
- Usage；
- needs/effects；
- Executor Profile。

### 3.3 Runs

全局运行记录。回答：

> 哪些流程运行过？哪里需要处理？

显示：

- 状态；
- Flow；
- 触发时间；
- 持续时间；
- 当前节点/失败节点；
- 是否有审批；
- 是否需要 reconciliation。

### 3.4 Resources

管理可绑定资源：

- Repository；
- Mailbox；
- Database；
- File Set；
- External Service。

资源不是产品中心对象，只作为 Flow 的运行绑定对象。

### 3.5 Governance

集中管理：

- Executor Profile；
- Effects Policy；
- Approval Policy；
- Audit / Export；
- 权限和组织策略。

### 4.1 Shell 规则

- 左侧导航桌面端固定宽度 224px；移动/窄屏折叠为抽屉；
- 顶部只放全局搜索、通知和账号，不放复杂工具条；
- 面包屑只显示两级：`Flows / 客户周报`；
- 页面标题下只允许一个简短说明；
- 页面右上角最多一个主按钮和一个次按钮；
- 技术信息不放在全局 Header。

## 5. 视觉系统

### 5.1 视觉方向

关键词：

```text
安静、清晰、可靠、克制、带一点专业感
```

不使用：

- 霓虹发光；
- 大面积渐变；
- 玻璃拟态；
- 装饰性网格背景；
- 高饱和多色卡片；
- 大量圆角嵌套；
- “AI 魔法”式动画。

### 5.2 颜色

以浅色工作台为默认，颜色只承担层级和状态：

```text
Canvas       #F7F8FA  页面背景
Surface      #FFFFFF  内容面板
SurfaceSubtle #F1F3F5 次级面板/侧栏
Border       #DDE1E6  边界
Text         #1F2933  主文本
TextMuted    #68737D  辅助文本
Primary      #315ECA  主要操作/当前选择
Success      #2F7D55  成功
Warning      #A56A14  等待/注意
Danger       #B54747  失败/危险
Info         #32758A  信息
```

规则：

- Primary 只用于主操作、当前选中和关键链接；
- 状态不只用颜色，同时显示文字和图标；
- 危险操作使用 Danger，但不大面积涂红；
- 暗色模式可后续增加，不在 MVP 同时维护两套视觉语言。

### 5.3 字体与密度

- 使用一个清晰的 UI 无衬线字体族；优先系统字体或已批准的产品字体；
- 正文 14px；辅助信息 12px；页面标题 24px；区域标题 16px；
- 不使用展示字体、等宽字体或大号数字作为品牌装饰；
- 等宽字体只用于 hash、命令、JSON、Trace ID；
- 页面密度为中等：让用户一次看到主要流程，不用卡片堆满屏幕；
- 8px spacing grid：4/8/12/16/24/32/48。

### 5.4 形状

- 基础控件圆角 6px；
- 面板圆角 8px；
- 不使用多层卡片套卡片；
- 阴影只用于浮层和抽屉，使用低对比、柔和阴影；
- 边框比阴影更常用；
- 图标统一使用同一套 SVG 图标，禁止 emoji 作为图标。

## 6. 首页：Flows

### 6.1 页面目标

用户进入首页后 5 秒内知道：

- 我有哪些 Flow；
- 哪些需要处理；
- 如何新建一个 Flow。

### 6.2 布局

```text
Flows                                      [新建 Flow]
管理可重复运行的工作流程

[需要处理 2] [运行中 1] [草稿 3] [最近失败 1]

最近的流程
┌─────────────────────────────────────────────────────────────┐
│ 客户周报                              已发布   昨天运行     │
│ 读取邮件与 CRM，整理风险并生成周报       [运行] [打开]       │
├─────────────────────────────────────────────────────────────┤
│ 代码变更审核                            草稿     2小时前修改  │
│ 分析变更、执行测试并请求人工审核         [继续编辑]          │
└─────────────────────────────────────────────────────────────┘
```

```text

[新建 Flow]
```

## 7. 新建 Flow：两条入口，一条流程

### 7.1 入口

新建 Flow 页面提供两个选择：

```text
从目标开始                         从模板开始
用一句话描述你想完成的工作           选择一个已有模板修改
```

默认突出“从目标开始”，但不隐藏“空白开始/模板开始”。

### 7.2 目标输入

```text
你想完成什么？
┌─────────────────────────────────────────────────────────────┐
│ 例如：每周读取客户邮件和 CRM 更新，整理风险并生成周报。     │
│                                                             │
└─────────────────────────────────────────────────────────────┘

可选：这个流程需要访问什么？
[选择资源] [添加约束]

                                      [生成流程草案]
```

交互规则：

- 不要求用户先选择 Agent；
- 不要求用户填写 DSL；
- 不在此处承诺成本、准确率或完成时间；
- 生成期间显示“正在整理可用能力”，不显示复杂 Agent 思考过程。

### 7.3 Proposal 审阅页

Proposal 页面不是聊天窗口，而是可编辑的流程草案。

```text
流程草案                         [保存草稿] [接受并编辑]
根据你的目标，我们建议 4 个步骤

目标理解
读取客户信息 → 整理风险 → 人工确认 → 生成周报

流程步骤
┌────┐  ┌────┐  ┌────┐  ┌────┐
│读取│→ │整理│→ │确认│→ │生成│
│邮件│  │风险│  │风险│  │周报│
└────┘  └────┘  └────┘  └────┘

选中步骤：整理风险
为什么选择：能够接收邮件和 CRM 的结构化结果
输入：邮件数据、CRM 数据
输出：风险等级、风险事项、周报数据
需要：CRM 读取权限

[替换能力] [删除步骤]
```

普通用户看到的文案：

- “为什么选择”；
- “需要什么”；
- “会产生什么影响”；
- “下一步会得到什么”。

技术用户可以展开：

- CFVersion；
- Executor Profile；
- capabilities；
- effects；
- programHash。

### 7.4 缺失能力

不显示伪造的步骤。显示：

```text
还缺少一个能力
系统没有找到“检查 API 兼容性”的已发布能力。

你可以：
[创建这个能力] [移除此步骤]
```

创建后，Flow 中保留“能力待完成”占位，不能测试或发布整个 Flow，直到 CF 发布并完成 resolve。

## 8. Flow Editor：少量结构，清晰操作

### 8.1 页面目标

用户能够回答：

- 流程先做什么、后做什么；
- 哪一步需要人工确认；
- 每一步的输入和输出是什么；
- 流程能否测试和发布。

### 8.2 布局

```text
客户周报 · 草稿                         [测试] [发布]
已修改 2 分钟前

┌──────────────────────┬──────────────────────────────────────┐
│ 步骤                  │                                      │
│                       │        Flow Canvas                  │
│ + 添加步骤            │                                      │
│                       │  [读取邮件] → [读取 CRM]              │
│ 步骤列表              │          ↘     ↙                    │
│ ✓ 读取邮件            │           [整理风险]                  │
│ ✓ 读取 CRM             │                ↓                     │
│ ! 人工确认             │           [人工确认]                  │
│ ✓ 生成周报            │                ↓                     │
│                       │           [生成周报]                   │
│                       │                                      │
└──────────────────────┴──────────────────────────────────────┘
```

### 8.3 左侧步骤列表

左侧列表是主要导航，画布是关系展示，不要求用户直接在画布上完成所有编辑。

每行显示：

- 状态图标；
- 步骤名称；
- 类型：能力/人工确认/分支/汇合；
- 是否有错误。

点击列表项：

- 画布定位该节点；
- 右侧打开详情；
- 不跳转页面。

### 8.4 添加步骤

“添加步骤”打开一个轻量抽屉，不打开全屏复杂对话框：

```text
添加步骤

搜索能力
[输入“读取邮件”                         ]

推荐
[读取客户邮件]  读取指定邮箱中的邮件
[整理客户信息]  根据结构化输入生成摘要

结构
[条件分支] [人工确认] [汇合]

[取消]
```

推荐能力必须显示：

- 一句话说明；
- 输入摘要；
- 输出摘要；
- 资源/权限提示。

不在列表里直接展示 Agent 名称，除非用户打开“技术详情”。

### 8.5 节点详情抽屉

```text
整理风险
根据邮件和 CRM 信息整理风险事项

输入
邮件数据、CRM 数据

输出
风险等级、风险事项、周报数据

它会访问
CRM · 读取

下一步
人工确认

[替换能力] [查看技术详情]
```

高级详情：

- CFVersion；
- programHash；
- Executor Profile；
- effects；
- timeout/retry；
- 输入/输出契约。

### 8.6 Binding 编辑

不让用户编辑 `$3.output.riskLevel` 之类的表达式。

使用字段选择器：

```text
整理风险 → 输入

邮件数据    ← 读取客户邮件 / 邮件结果
CRM 数据    ← 读取 CRM / CRM 结果

[添加输入]
```

高级用户可以查看“技术引用”，但默认使用“来源 → 目标”的自然语言表达。

### 8.7 分支和汇合

默认交互使用句子：

```text
如果风险等级是高风险 → 需要人工确认
否则 → 直接生成周报
```

不要让普通用户先理解 `branch-case`、`any`、`quorum`。

高级设置中再显示：

```text
分支类型：互斥分支
汇合策略：全部完成 / 任一完成 / 达到数量
```

### 8.8 编辑器中的发布门禁

发布按钮旁显示简短状态：

```text
[测试通过] [发布]
```

如果不能发布：

```text
还不能发布
需要处理 2 项问题

[查看问题]
```

问题按用户能理解的顺序排列：

1. 缺少能力；
2. 输入没有连接；
3. 资源未绑定；
4. 权限或副作用未确认；
5. 测试未通过；
6. unresolved placeholder。

每个问题都提供直接操作，不只显示错误码。

## 9. 测试 Flow

### 9.1 测试前检查

点击“测试”后先显示运行前摘要，而不是直接执行：

```text
测试这个流程

将执行：
读取邮件 → 读取 CRM → 整理风险 → 人工确认 → 生成周报

需要访问：
邮箱 · 读取
CRM · 读取

可能产生：
周报文件 · 写入

[开始测试] [返回修改]
```

测试模式：

- 默认使用沙箱；
- effects 默认模拟；
- 需要真实资源时必须明确显示；
- 不自动把测试结果发布成正式版本。

### 9.2 测试结果

```text
测试完成                                      [查看完整运行]

✓ 读取客户邮件       12 秒
✓ 读取 CRM            4 秒
✓ 整理风险            18 秒
! 人工确认             跳过（测试模式）
✓ 生成周报             7 秒

结果
已生成一份示例周报

[查看结果] [返回编辑] [发布这个版本]
```

### 9.3 失败结果

```text
测试未完成
整理风险这一步没有通过输入检查。

问题：缺少“CRM 数据”
建议：连接“读取 CRM”的输出，或修改该能力的输入。

[修复连接] [查看详情]
```

错误文案必须包含：

```text
发生了什么
为什么发生
用户下一步可以做什么
```

## 10. 发布 Flow

发布不是危险弹窗，而是最后一次清晰确认。

```text
发布“客户周报”

这次发布会固定：
• 4 个步骤
• 2 个资源访问
• 1 个人工确认
• 1 个写入操作

以后运行会使用这一版流程。
当前版本：1.2.0

[返回修改] [确认发布]
```

高级展开：

- FlowVersion；
- planHash；
- 精确 CFVersion；
- Executor Profile；
- effects；
- 语义 Diff；
- 测试快照。

发布完成后显示：

```text
已发布
客户周报 · v1.2.0

[运行一次] [查看流程]
```

## 11. Run Viewer

### 11.1 页面目标

普通用户只需要知道：

- 流程是否完成；
- 现在卡在哪里；
- 是否需要我处理；
- 最终结果在哪里。

### 11.2 默认布局

```text
客户周报 · 运行中                     [停止运行]
正在等待你的确认

┌─────────────────────────────────────────────────────────────┐
│ 读取邮件 ✓  → 读取 CRM ✓ → 整理风险 ✓ → 人工确认 ! → 生成报告 │
└─────────────────────────────────────────────────────────────┘

需要你的操作
风险较高，需要确认后才能生成正式周报。

[查看风险] [批准并继续] [拒绝]
```

完成后：

```text
客户周报 · 已完成
完成于今天 10:42 · 用时 46 秒

结果
[打开周报]

流程步骤
读取邮件 ✓ → 读取 CRM ✓ → 整理风险 ✓ → 人工确认 ✓ → 生成报告 ✓

[查看运行详情] [再次运行]
```

### 11.3 DAG 视图

DAG 是默认技术视图，但节点只显示业务名称：

- 当前节点突出；
- 未选分支显示为灰色 inactive；
- blocked 显示“等待前置步骤”；
- failed 显示具体恢复动作；
- needs-reconciliation 显示橙色警示和“需要确认”。

### 11.4 Waterfall 视图

Waterfall 是性能视图，不是默认视图：

```text
[业务流程] [执行时间]
```

执行时间视图显示：

- CF 调用持续时间；
- 并行关系；
- 失败/重试；
- 成本（若可用）；
- 高级展开后才显示 Agent/LLM/Tool。

### 11.5 右侧详情抽屉

默认显示：

- 发生了什么；
- 输入输出摘要；
- 当前状态；
- 下一步；
- 是否有权限/副作用。

技术详情折叠：

- CFVersion；
- programHash；
- FlowVersion；
- planHash；
- Trace ID；
- Run Ledger 记录；
- Executor Profile；
- Agent/Tool span。

### 11.6 不同运行状态的文案

| 状态 | 普通用户文案 | 操作 |
|---|---|---|
| running | 正在处理“整理风险” | 查看进度/停止 |
| waiting-approval | 需要你的确认才能继续 | 查看/批准/拒绝 |
| failed | “整理风险”没有完成 | 查看原因/重试 |
| blocked | 等待前面的步骤完成 | 查看前置步骤 |
| inactive | 这条路径没有被选中 | 无 |
| needs-reconciliation | 外部操作结果需要确认 | 回读/补偿/安全重试/终止 |
| completed | 流程已完成 | 查看结果/再次运行 |
| cancelled | 流程已停止 | 查看已完成部分 |

## 12. 处理 needs-reconciliation

这是唯一需要稍微复杂一点的治理交互，但必须用普通语言表达：

```text
需要确认外部操作

系统无法确认“发送周报邮件”是否已经完成。
为了避免重复发送，流程已暂停，后续步骤不会继续。

请选择：

[检查是否已发送]
读取目标系统的实际状态，不重新执行操作。

[确认已发送]
将这次操作记为已完成并继续流程。

[安全重试]
仅在你确认目标系统支持重复操作安全时使用。

[终止流程]
保留当前运行记录，不再继续。
```

不要把 `effectState=unknown`、`idempotencyKey`、adapter crash 等内部词作为主文案。

## 13. CF Library 前端

### 13.1 CF 列表

```text
CF Library                                  [创建能力]

搜索能力
[输入“读取邮件、生成报告...”                  ]

能力名称             用途                  状态      使用中
读取客户邮件         读取指定邮箱            已发布    4 个流程
整理风险             识别风险事项            已发布    2 个流程
检查 API 兼容性      检查接口变更            草稿      未使用
```

### 13.2 创建 CF

使用四步工作流：

```text
1. 说明能力
2. 确认输入输出
3. 测试能力
4. 发布能力
```

#### 第一步：说明能力

```text
这项能力要做什么？
[从客户邮件中提取风险事项                         ]

需要什么输入？
[邮箱中的邮件、客户范围                           ]

会产出什么？
[风险等级、风险事项、摘要                         ]

可选：补充执行过程
[先读取邮件，再按规则提取风险...                   ]
```

#### 第二步：确认输入输出

系统生成结构化契约建议，但用人话展示：

```text
系统理解为：
输入：邮件列表、客户范围
输出：风险等级、风险事项、摘要

[接受] [修改描述]
```

不要默认显示 JSON Schema。点击“查看技术格式”再展开。

#### 第三步：测试能力

显示 CF Test Snapshot 的业务信息：

```text
这次测试使用的是当前草稿的临时快照。
测试结果不会自动发布能力。

[运行测试]
```

#### 第四步：发布能力

```text
发布能力“整理风险”

固定：
• 输入和输出格式
• 需要的资源权限
• 执行过程
• 可用的执行器

[发布]
```

### 13.3 CF 详情页

标签页保持五个：

```text
说明 | 编译 | 测试 | 版本 | 使用情况
```

其中：

- 说明：普通用户主要使用；
- 编译：显示步骤摘要和 source map；
- 测试：显示 Snapshot 和结果；
- 版本：语义 Diff；
- 使用情况：被哪些 Flow 引用。

## 16. 状态、错误和空状态规范

### 16.1 状态标签

所有状态同时使用：

- 图标；
- 文案；
- 颜色；
- 必要时辅助说明。

不依赖颜色单独表达状态。

### 16.2 错误文案模板

```text
标题：发生了什么
说明：为什么发生
行动：下一步怎么修复
```

示例：

```text
无法发布流程
“整理风险”缺少“CRM 数据”输入。
连接“读取 CRM”的输出，或替换这个能力。

[修复连接]
```

### 16.3 空状态模板

```text
没有内容
这说明什么
[最相关的下一步]
```

禁止：

- “暂无数据”；
- 没有操作的空白页；
- 只放插画不解释产品行为。

### 16.4 Loading

- 页面级内容使用骨架屏；
- 操作按钮显示进行中状态并禁止重复点击；
- 不展示无限旋转的“AI 思考”动画；
- 长任务显示阶段和当前步骤。

### 16.5 Toast

只用于：

- 保存成功；
- 复制成功；
- 导出开始；
- 非阻断提示。

失败、权限、审批和副作用不能只用 Toast 表示。

## 17. 响应式设计

### 17.1 Desktop ≥ 1200px

- 左侧导航 224px；
- Flow Editor：步骤列表 240px + 画布 + 详情抽屉 320px；
- Run Viewer：主视图 + 详情抽屉；
- 内容最大宽度 1440px。

### 17.2 Tablet 768–1199px

- 左侧导航折叠；
- 详情抽屉变为右侧浮层；
- Flow Editor 步骤列表可折叠；
- 画布最小可用宽度不低于 560px。

### 17.3 Mobile < 768px

移动端不是缩小桌面画布：

```text
顶部：标题 + 主操作
下方：步骤列表
点击步骤：进入步骤详情
点击“查看流程”：进入只读纵向流程
```

- Flow Editor 默认使用纵向步骤列表；
- DAG 作为可横向滚动的只读关系图；
- Binding 使用上下两组字段，不显示连线；
- Run Viewer 默认使用线性步骤时间线；
- Waterfall 为可选高级视图，不作为默认入口；
- 详情使用全屏 Sheet；
- 所有触控目标至少 44×44px。

## 18. 无障碍与键盘操作

必须支持：

- 键盘访问所有主流程；
- 清晰 focus ring；
- Tab 顺序与视觉顺序一致；
- 画布节点有可访问名称和状态；
- 颜色之外的状态表达；
- 弹层打开后焦点进入弹层，关闭后回到触发按钮；
- `Esc` 关闭抽屉/弹层；
- `prefers-reduced-motion` 下减少动画；
- 文案不依赖图标猜测；
- 错误信息使用 `aria-live` 通知，但不打断长任务阅读。

---

## 19. 动效规范

Operate 型产品只使用表达状态的动效：

- 抽屉打开：150–200ms；
- 节点状态变化：颜色/边框/图标变化，150–250ms；
- 运行节点：轻微脉冲，不持续跳动；
- 分支激活：边线短暂强调；
- 保存成功：按钮状态变化；
- 页面加载：骨架屏，不做整页入场编排。

禁止：

- 每个节点同时动画；
- 无限闪烁；
- 为了“AI 感”增加粒子、光晕或流光；
- 把重要内容藏在动画结束后。

## 23. 明确不做

MVP 不做：

- 直接编辑 FlowPlan JSON；
- 直接编辑 CFProgram JSON；
- 运行时动态添加节点；
- 自动把 Agent 换成另一个 Agent；

- 多窗口复杂编排；
- 过度拟物化的 Agent 动画；

- 通过颜色 alone 表达状态；
- 让用户输入 `$N.output` 之类的内部引用；
- 用 Shared Memory 替代 Binding；
- 隐式 Coordinator 综合；
- 把未发布 ProposedCFDraft 当作可执行能力。

## 24. 前端验收标准

### 可理解性

- 新用户能在不阅读 DSL 文档的情况下创建一个简单 Flow；
- 页面主按钮始终明确；
- 每个错误都提供下一步操作；
- 普通用户不会被 Agent/Trace/Hash 术语阻塞。

### 架构一致性

- 业务 UI 编辑 CFDraft/FlowDraft；
- CFProgram/FlowPlan 只读；
- 所有跨节点数据都通过 Binding；
- 分支和错误路由可视化；
- Flow 节点不能扩大 CFVersion 权限；
- Run Viewer 的治理事实来自 Receipt/Run Ledger；
- Executor Profile 版本固定在发布版本中。

### 可靠性

- 发布前能看见资源、权限、effects；
- 外部副作用未知时不会自动重试；
- failed、blocked、inactive、needs-reconciliation 有不同状态；
- 测试不等于发布；
- 保存、发布、运行、审批、导出都能看到明确反馈。

### 视觉与交互

- 桌面和移动端都能完成核心路径；
- 颜色对比符合 WCAG AA；
- 所有交互控件有 focus/disabled/loading/error 状态；
- 动效服务于状态，不制造等待；
- 不使用多层卡片、渐变文字、玻璃拟态和装饰性 Agent 动画；
- 视觉层级克制，用户一眼能找到当前任务。

## 26. 最终 UI 判断

如果一个用户只看到了三个页面，他应该能理解整个产品：

```text
Flow 列表：我有什么流程
Flow 编辑：这个流程怎么工作
Run 详情：这次运行发生了什么
```

所有高级能力都围绕这三个页面渐进展开。

最终前端应该让用户感觉：

> “我只是在搭一个清晰的工作流程。”

而不是：

> “我正在操作一个复杂的多 Agent 编排引擎。”

这就是本产品前端设计的核心判断。
